# Сервис сопровождения пациента

`medmarshrut_path_service` принимает **только подписанное подтверждённое заключение** от сервиса снимков, создаёт `Episode` и хранит `SourceReport`, `PlanStep`, `AuditEvent` в SQLite. Сервис слушает `127.0.0.1:8765`. После перезапуска эпизоды читаются из того же файла базы. По умолчанию `rules.json` не содержит утверждённых клиникой правил: каждый принятый отчёт требует ручного разбора.

## Запуск

Из корня репозитория в двух PowerShell окнах задайте одинаковый секрет межсервисного обмена (не менее 16 символов). Токен администратора должен отличаться от него.

```powershell
$env:PATH_SHARED_SECRET = 'replace-with-random-shared-secret'
$env:PATH_ADMIN_TOKEN = 'replace-with-random-admin-token'
$env:PATH_DB = 'D:\local-state\path.sqlite3'
$env:PATH_RULES = 'D:\projects_X\Just-Business-Darling\medmarshrut_path_service\rules.json'
python .\medmarshrut_path_service\service.py
```

Для сервиса снимков дополнительно:

```powershell
$env:REVIEWER_TOKEN = 'replace-with-random-reviewer-token'
$env:PATH_SHARED_SECRET = 'replace-with-random-shared-secret'
$env:ROUTER_URL = 'http://127.0.0.1:8765/v1/reports'
python .\medmarshrut_image_service\service.py
```

Базовые зависимости сервиса снимков установите из его `requirements.txt`; сервис сопровождения использует стандартную библиотеку Python. `PATH_DB` должен указывать на локальную папку с ограниченным доступом. Не храните реальную базу и секреты в репозитории.

## Межсервисный контракт

После `POST /v1/review/{id}` сервис снимков отправляет `POST /v1/reports` с JSON:

```json
{
  "source_service":"medmarshrut_image_service", "source_report_id":"job-123", "source_report_version":1,
  "confirmation_status":"confirmed", "physician_id":"doctor-1", "confirmed_at":"2026-10-03T12:00:00+00:00",
  "study_type":"mr", "study_uid":"1.2.3.4", "patient_ref":"pseudonym-1",
  "anatomy":"BRAIN", "protocol_name":"MR_BRAIN", "finding_code":"FINDING_X",
  "conclusion":"Заключение после проверки врачом", "confidence":0.72, "source_model":"model-v1"
}
```

Поддерживаются `ct`, `mr`, `mammography`. `patient_ref` — псевдоним, который врач или доверенная система может передать при подтверждении; он не извлекается автоматически из DICOM `PatientID`. Без него эпизод создаётся с задачей ручного разбора. `confidence` сохраняется как происхождение вывода модели и **не используется для срочности или выбора плана**. Для реального пациента решение требует отдельной клинической идентификации и проверки.

Тело запроса — UTF-8 JSON, максимум 16 КиБ. Заголовки: `X-Path-Timestamp` (Unix seconds) и `X-Path-Signature` (`sha256=` + hex HMAC-SHA256 по `timestamp + '.' + raw_body`, ключ `PATH_SHARED_SECRET`). Допуск по времени ±300 с. Подпись проверяется до создания эпизода. Повтор той же пары `(source_service, source_report_id, source_report_version)` с тем же содержимым возвращает `200` и тот же `episode_id`; новая запись возвращает `201`. Другое содержимое под тем же ключом возвращает `409`. Новая версия заключения создаёт отдельный эпизод с задачей ручного согласования с предыдущим; второй план автоматически не создаётся. Ошибка подписи — `403`; черновик или отсутствие данных подтверждения — `400`.

Псевдоним врача и время подтверждения — поля события, а межсервисная подпись доказывает отправителя, не личность врача. Токен врача контролируется сервисом снимков.

## Правила и сопровождение

`rules.json` имеет `version`, `supported_protocols` и `rules`. Область правила — точная комбинация `study_type`, `anatomy`, `protocol_name`, `finding_code`. Пример **неутверждённого** правила:

```json
{
  "version":"clinic-rules-v1",
  "supported_protocols":[{"study_type":"mr","anatomy":"BRAIN","protocol_name":"MR_BRAIN"}],
  "rules":[{"study_type":"mr","anatomy":"BRAIN","protocol_name":"MR_BRAIN",
    "finding_code":"FINDING_X","approved":false,
    "steps":[{"kind":"appointment","description":"Рассмотреть врачом профильной специальности"}]}]
}
```

Изменение `approved` на `true` — действие уполномоченной клиники после проверки правила; изменяйте `version` при каждой редакции и перезапускайте сервис. Неподдерживаемый протокол, неизвестный код, отсутствие утверждённого правила или `patient_ref` создают `manual_review` и шаг ручной проверки. Допустимые виды шагов: `appointment`, `test`, `follow_up`, `care_coordination`; `manual_review` создаёт сервис. Не задавайте срочность по одной вероятности модели.

С `Authorization: Bearer <PATH_ADMIN_TOKEN>` доступны:

- `GET /v1/episodes` — до 100 последних идентификаторов;
- `GET /v1/episodes/{id}` — эпизод, источник, шаги и журнал;
- `POST /v1/episodes/{id}/manual-plan` — `{"actor":"doctor-1","steps":[{"kind":"follow_up","description":"..."}]}`;
- `POST /v1/episodes/{id}/steps/{step_id}` — завершение только административного шага `care_coordination` с `{"actor":"coordinator","evidence":"..."}`; клинический шаг завершается подтверждённым итогом визита;
- `POST /v1/episodes/{id}/close` — `{"actor":"doctor-1","outcome":"..."}` после завершения всех шагов.

`POST /v1/episodes` — подписанный псевдоним `POST /v1/reports` для создания эпизода из заключения. Ручной план добавляется только человеком после рассмотрения задачи. Типизированный интерфейс `CandidateProposer` в `candidates.py` допускает будущие локальные NLP/ML-предложения, но они не меняют `PlanStep` и не закрывают эпизод.

## Повторяемый цикл и интерфейсы

Компоненты: сервис снимков → подписанное заключение → `EpisodeStore` (SQLite: эпизоды, шаги, журнал, входящие итоги, исходящие события) → API пациента и API сотрудника. МИС или форма сотрудника передаёт подтверждённый врачом итог после состоявшегося визита. Только этот итог добавляет следующий шаг. Настроенные клиникой правила могут создать начальный план; поставляемый `rules.json` пуст и не утверждает ни одного медицинского действия.

`PlanStep` хранит ответственного `owner`, статус, срок `due_at` или условие `continue_on`, источник решения `decision_source`, номер цикла и время записи. История переходов находится в `audit_events`. Типичный порядок: `open → offered → confirmed → attended → completed`; последний переход выполняет только подтверждённый итог. Итог может содержать несколько следующих консультаций или исследований. Следующее предложение записи доступно лишь после завершения предыдущего шага. `cancel`, `refuse` и `lost_contact` останавливают эпизод (`paused`) и помещают его в очередь; врач может заменить план через `revise-plan`. Заменённые шаги остаются в истории как `superseded`. Закрытие доступно после завершения всех действующих шагов.

API сотрудника с `PATH_ADMIN_TOKEN`:

- `POST /v1/episodes/{id}/steps/{step_id}/{offer|confirm|attend|cancel|refuse|lost_contact}`: `actor`, `evidence`; для `offer` обязателен `appointment_at`, опционален `due_at` (ISO 8601 с часовым поясом).
- `POST /v1/episodes/{id}/revise-plan`: `physician_id`, `reason`, `steps`.
- `POST /v1/episodes/{id}/stop`: `actor`, `reason`; закрывает эпизод, в том числе после отказа или потери связи, сохраняя незавершённые шаги в истории.
- `GET /v1/staff/queue`: случаи ручного разбора, остановки, просрочки и ожидания итога; `GET /v1/staff/metrics`: показатели; `GET /v1/staff/outbox`: локальные исходящие события. Отправки пациентам нет.
- `GET /v1/rules`: загруженные правила и версию, включая неутверждённые; нужен `PATH_ADMIN_TOKEN`.
- `POST /v1/rules/dry-run`: проверить сочетание `study_type`, `anatomy`, `protocol_name`, `finding_code` без создания эпизода; нужен `PATH_ADMIN_TOKEN`.

Итог МИС отправляется с `PATH_MIS_TOKEN`, итог формы сотрудника — с `PATH_ADMIN_TOKEN`, на `POST /v1/episodes/{id}/outcomes`. Тело: `{"step_id":"...","outcome":{"source":"mis|staff_form","event_id":"...","physician_id":"...","confirmed_at":"2026-10-04T11:00:00+00:00","summary":"...","next_steps":[{"kind":"appointment","description":"...","owner":"coordinator-1","due_at":"2026-10-10T12:00:00+00:00","continue_on":"confirmed_outcome"}]}}`. Пустой `next_steps` означает завершение плана; эпизод затем закрывает сотрудник. Ключ `(source,event_id)` идемпотентен, а повтор с другим содержимым отклоняется. Интеграция МИС должна передавать факт визита отдельно через `attend` и итог только после подтверждения врачом. Сервис доверяет роли интеграции; проверка подлинности врача должна быть в МИС или форме.

API пациента: `GET /v1/patient/{patient_ref}` возвращает только «что сделать сейчас» и историю шагов без текста заключения и внутреннего журнала. Токен `Bearer` — HMAC-SHA256 от `patient_ref` с секретом `PATH_PATIENT_TOKEN` (hex). Выдача токена и связывание псевдонима с личностью пациента остаются обязанностью доверенного портала. Для локального демо задайте секреты `PATH_PATIENT_TOKEN` и `PATH_MIS_TOKEN` в окружении; при пустом значении соответствующая роль отключена.

Браузерные страницы локального демо: `/patient` и `/staff`. Они запрашивают токен при открытии, показывают текущий шаг и историю или очередь с причинами и доступными действиями. Страница сотрудника открывает подробности случая; запись действий выполняется через API. Токены на страницах не сохраняются.

Метрики по всем эпизодам локальной базы: среднее время от подтверждения заключения до первого предложения записи, доля предложенных шагов, доля подтверждённых предложений, число состоявшихся визитов, число незавершённых эпизодов и доля эпизодов с ручным утверждением или сменой плана. `route_quality` показывается отдельно: число и доля эпизодов с ошибкой или отсутствием утверждённого маршрута. Это операционные показатели демо, не клиническая оценка качества лечения.

## Сквозное демо

```powershell
python -B .\medmarshrut_path_service\demo_two_cycles.py
```

Без `--db` скрипт создаёт временную базу и печатает JSON. С `--db <новый_файл>` сохраняет базу для браузерного сервиса; существующий файл не перезаписывает. Сценарий: синтетическое заключение → врач вручную задаёт первую консультацию → первая запись → состоявшийся визит → подтверждённый итог с назначенным врачом следующим исследованием → вторая запись. В выходе видны два цикла, источники решений, пациентский интерфейс, метрики и локальная очередь исходящих событий. Если задан `PATH_PATIENT_TOKEN`, выводится вычисленный токен для синтетического пациента. Тесты переходов: `test_workflow.py`.

Перед пилотом клиника должна утвердить каждое правило и версии маршрутов, проверить договор событий МИС и подтверждения визита/итога, роли и персональную авторизацию сотрудников, привязку пациента к псевдониму, доставку и дедупликацию событий, защиту данных, резервное копирование, мониторинг просрочек и критерии оценки ошибок направления. В демо нет реальной отправки сообщений, интеграции МИС, индивидуальной аутентификации сотрудников, полного журнала чтений и продукционного планировщика просрочек. Очередь просрочек вычисляется при чтении.

## Ограничения демо и тесты

Это локальный прототип. Отсутствуют интеграция с МИС, подтверждение личности пациента, распределённая доставка/повторные отправки после перезапуска сервиса снимков, клинически утверждённый набор правил, журнал доступа к чтению и эксплуатационные средства защиты медицинских данных. SQLite хранит чувствительное заключение в открытом виде; для реального контура нужны шифрование, резервное копирование, роли, аудит доступа и защищённый транспорт. Сервис снимков хранит свои задания только в памяти. Ответственный врач остаётся источником окончательного маршрута.

```powershell
python -B -m unittest discover -s .\medmarshrut_path_service -p 'test_*.py' -v
python -B -m unittest discover -s .\medmarshrut_image_service -p 'test_*.py' -v
```
