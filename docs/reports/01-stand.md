# 01. Демо-стенд: отчёт

## Что сделано

- `start.py` в корне поднимает сервисы пути (8765), клиники (8764) и снимков (8766), ждёт их `/health`, наполняет стенд и работает до Ctrl+C. Процессы описаны списком `SERVICES` в начале файла: шлюз из задания 02 добавляется туда одной записью.
- `demo_stand/` — всё для демонстрации:
  - `synthetic_dicom.py` — генератор учебных исследований: рисунки 256×256 (градиент и круги), без тегов пациента. 14 архивов: по одному на семь пациентов наполнения, пять `upload-*` для загрузки из интерфейса, два `smoke-*` для смоук-проверки. Пишет `kit/index.json` (UID → признаки) и `kit/kit.json` (каталог архивов).
  - `image_demo_runner.py` — сервис снимков со сценарным backend, по заготовке из задания без изменений логики.
  - `rules.demo.json`, `network.demo.json`, `people.demo.json`, `conclusions.demo.json` — данные стенда по таблицам задания.
  - `seed.py` — наполнение только через публичные API; пишет реестр `studies.json` (идентификатор задания → `patient_ref`, название исследования, вид, имя архива).
  - `smoke.py` — сквозная проверка из десяти шагов на пациенте `smoke-<hex>`.
  - `stand_api.py` — общий HTTP-клиент `seed.py` и `smoke.py` (подписи, токены, разбор ответов).
  - `README.md` — что такое стенд, флаги, что учебное, почему backend сценарный.
- `.gitignore`: `*.sqlite3`, `*.sqlite3-*` для всех папок.
- Корневой `README.md`: раздел «Запуск стенда одной командой». Остальной текст не тронут.
- `docs/api-contracts.md`: условие `offer` описано по исправленному коду.

## Правки в чужом коде

- `medmarshrut_path_service/store.py`, `EpisodeStore.transition`: условие перед `offer` считает завершёнными шаги `completed` и `superseded` (было — только `completed`). Одна строка.

В сервисах снимков и клиники изменённых строк нет. Кодировка `store.py` (BOM) сохранена.

## Что важно знать следующим заданиям

- Переменные окружения для скриптов стенда: секреты под теми же именами, что у сервисов (`PATH_ADMIN_TOKEN`, `REVIEWER_TOKEN`, `CLINIC_SHARED_SECRET`, `CLINIC_STAFF_TOKENS` и т. д.), плюс `DEMO_STATE_DIR` и `DEMO_IMAGE_MODE` (`demo` или `real`). `start.py` передаёт их дочерним процессам; каждый сервис получает только свои.
- `CLINIC_STAFF_TOKENS` — JSON «токен → `clinic_id`» для трёх клиник; токен клиники ищется обратным поиском (`stand_api.staff_token`).
- Сервис пути получает ещё `PATH_PATIENT_TOKEN`: встроенная страница пациента работает. `PATH_MIS_TOKEN` и `CLINIC_MIS_TOKEN` не заданы, роль МИС выключена.
- `studies.json` — словарь `job_id → {"patient_ref", "title", "kind", "kit"}`. Задания смоук-проверки в него не попадают.
- `people.demo.json`: `staff` (все сотрудники и демо-роли с `clinic_id`), `roles` (`staff`, `doctor`, `partner` по клиникам, `patient`), `patients` (`patient_ref`, `name` для интерфейса, `full_name` для карты, дата рождения, пол, контакт).
- Наполнение подтверждает снимки от имени рентгенолога `radiologist-ershov`, смоук-проверка — от `doctor-demo`.
- Порядок запуска в `SERVICES`: путь, клиника, снимки. Сервис снимков отправляет заключение в сервис пути только при подтверждении, поэтому порядок не критичен.

## Ограничения

- Если закрыть окно консоли крестиком, а не Ctrl+C, дочерние процессы могут остаться жить: они запущены в своей группе, чтобы Ctrl+C не ронял их раньше родителя. Следующий запуск скажет, что порты заняты. Тогда процессы `python` нужно завершить в диспетчере задач. Решение — Job Object Windows, если понадобится.
- `--keep` сохраняет базы, но задания сервиса снимков после перезапуска пропадают, и `studies.json` ссылается на несуществующие задания. Стенд об этом предупреждает.
- Время приёмов считается от момента наполнения в часовом поясе компьютера. Запись «на сегодня» у `demo-patient-4` — 16:30, а если наполнение позже, то через 15 минут от текущего времени.
- `--smoke` не сочетается с `--keep` и `--image real`: проверка рассчитана на чистый стенд со сценарным backend.

## Предложения команде

- Сервис снимков в ответ на подтверждение не сохраняет `episode_id`, поэтому эпизод ищется перебором `GET /v1/episodes` (до 100 последних). Для стенда хватает; шлюзу в задании 02 стоит кешировать соответствие.
- В очереди сервиса пути случай ручного разбора дополнительно получает причину `unfinished:<id>` для шага `manual_review`. Интерфейсу стоит её не показывать.
