# 02. Шлюз: отчёт

## Что сделано

- `medmarshrut_gateway_service/` — шлюз на `127.0.0.1:8763` в стиле остальных сервисов (stdlib, `ThreadingHTTPServer`, плоские импорты):
  - `service.py` — конфигурация из окружения, таблицы маршрутов и доступа, защита, статика из `web/`;
  - `sessions.py` — роли, сессии в памяти (по одной на роль, своя кука у каждой), люди стенда из `people.demo.json`, проверка `ensure_owner`;
  - `upstream.py` — клиенты трёх сервисов: bearer-токены, подпись (копия `signature` из сервиса пути), тайм-ауты, проверка типов до вызова, перевод ошибок сервисов на русский;
  - `errors.py` — `GatewayError` и формат `{"error": {"code", "message", "detail"?}}`. Файла нет в списке задания: ошибка нужна и сессиям, и клиентам, и обработчику, а отдельный модуль убирает циклические импорты;
  - `store.py` — SQLite шлюза `gateway.sqlite3` в папке состояния, таблиц пока нет;
  - `web/index.html`, `web/js/boot.js` — временная страница: выбор роли, состояние сервисов. Роль окна хранится в адресе (`#role=staff`): `localStorage` и `sessionStorage` запрещены;
  - `test_gateway.py` (26 тестов), `README.md`, `requirements.txt`.
- `start.py`: шлюз — четвёртый процесс, порт 8763 в проверке портов, адрес приложения печатается после старта. `GATEWAY_IMAGING_MODE` выводится из режима: `demo-scripted`, а с `--image real` — `model` при заданном `MODEL_CONFIG`, иначе `no-model`. Унаследованные переменные шлюза, адресов сервисов и токенов МИС вычищаются из окружения дочерних процессов.
- `start.py`, изменение поведения: если один процесс остановился, стенд больше не гасится целиком. `start.py` один раз сообщает, какой процесс упал, и показывает хвост его журнала, остальные продолжают работать. Без этого проверка из «Готово, когда» («остановить один сервис — страница показывает „недоступен“») была бы невозможна: раньше вместе с сервисом останавливался и шлюз.
- `demo_stand/smoke.py`: шаг 11 через шлюз — `/api/health` показывает три работающих сервиса и `demo-scripted`, сессия пациента создаётся, незарегистрированный псевдоним отклоняется.
- `demo_stand/README.md`: шлюз, порты 8763–8766, поведение при падении сервиса.

## Правки в чужом коде

Нет. Код сервисов снимков, пути и клиники не изменён.

## Маршруты и роли

| Маршрут | Роли |
|---|---|
| `GET /`, `GET /assets/...` | без сессии |
| `GET /api/health` | без сессии |
| `POST /api/session` | без сессии (нужны `X-MM-Role`, свой `Origin`, JSON) |
| `GET /api/session` | patient, staff, doctor, partner |
| `DELETE /api/session` | patient, staff, doctor, partner |

Порядок проверок: `Host` не из списка — 403; неизвестный путь — 404; для `POST`/`PUT`/`PATCH`/`DELETE` чужой `Origin` — 403, нет `X-MM-Role` — 401, тип не JSON — 415, тело больше 32 КиБ — 413 (по `Content-Length`, до чтения); нет сессии роли — 401; роли нет в `Gateway.access` — 403.

Новый маршрут: строка в `Gateway.routes` (обработчик) и строка в `Gateway.access` (роли). Без второй строки маршрут отвечает 403. В шаблоне пути можно писать `{id}`, значение придёт в `ctx.params`.

## Как проверить

```powershell
python -B -m unittest discover -s ./medmarshrut_gateway_service -p "test_*.py" -v
python start.py --smoke
python start.py   # затем http://127.0.0.1:8763
```

## Результаты

- Шлюз: 26 тестов, все проходят, около 8 секунд. Сервисы: 16, 10 и 5 тестов, все проходят.
- `python start.py --smoke`: 11 шагов из 11, код 0.
- В браузере (Chrome):
  - страница открывается, роль выбирается, все три сервиса «работает»;
  - две вкладки — «Сотрудник» и «Пациент» — работают одновременно и не теряют сессию после перезагрузки;
  - после ручной остановки процесса сервиса клиники он отмечен «недоступен», а вход пациентом показывает «Сервис клиники недоступен. Проверьте, что стенд запущен (python start.py).»;
  - в консоли нет нарушений CSP.

## Что важно знать следующим заданиям

- Обработчик получает `Context`: `role`, `session`, `body` (уже разобранный JSON), `params`, `cookies`. Возвращает `(status, dict)`. Ошибки — `raise GatewayError(...)`.
- Личность для сервисов — `ctx.session.actor` (id из `people.demo.json`: `coordinator-natalia`, `doctor-demo`, `partner1-coordinator`…), клиника — `ctx.session.clinic_id`, пациент — `ctx.session.patient_ref`.
- Вызов сервиса: `gateway.upstream.json("path", "GET", "/v1/staff/queue", auth="path_admin")` — вернёт словарь или поднимет понятную ошибку. Виды `auth`: `reviewer`, `path_admin`, `path_mis`, `clinic_signed`, `("clinic_staff", clinic_id)`. Для «сырого» ответа — `upstream.request(...)` и `upstream.human_error(...)`.
- Проверки типов перед вызовом: `upstream.text`, `upstream.patient_ref`, `upstream.boolean`.
- Новые тексты ошибок сервисов добавляются в `upstream.MESSAGES` (английская подстрока → русский текст).
- Исключение по типу тела для загрузки архива (задание 05) делается в `RequestHandler._handle`: сейчас там жёсткая проверка `application/json` для всех изменяющих запросов. Там же нужен свой лимит размера.
- Тайм-аут клиента — 10 секунд; для загрузки снимка передайте `timeout=` в `request`.

## Ограничения

- Пароля нет: роли выбираются кнопкой. Для пилота нужна настоящая аутентификация.
- Сессии в памяти: перезапуск шлюза завершает все сессии, страница снова попросит выбрать роль.
- На Windows подключение к закрытому порту повторяется около двух секунд, поэтому `/api/health` с остановленным сервисом отвечает примерно за 2 секунды (сервисы опрашиваются параллельно, тайм-аут 2 с).
- Упавший процесс `start.py` не перезапускает: нужен перезапуск стенда.
- Временная страница знает две клиники-партнёра из разметки, а не из API. Задание 03 её заменит.
