# 04. «Путь пациента» на настоящем сервисе

## Зачем

Это ядро кейса: заключение подтверждено врачом, сервис определяет следующий шаг, координатор и пациент доводят дело до записи, врач после приёма назначает следующий цикл. После задания 03 экраны маршрута работают на данных из памяти вкладки. Теперь их источником становится `medmarshrut_path_service`, а действия на экранах меняют настоящие эпизоды.

Это самое большое задание. Оно разбито на три этапа, каждый заканчивается рабочим продуктом и коммитом. Если пользователь назвал этап, сделай только его. Если не назвал, иди по порядку и останавливайся на границе этапа, когда видишь, что следующий не успеть сделать хорошо.

## База шлюза: первый шаг этапа 1

С задания 04 рабочие данные шлюза живут в PostgreSQL проекта Supabase. Браузер обращается только к шлюзу; сервисы пути и клиники пока остаются на SQLite, сервис снимков — в памяти. `medmarshrut_gateway_service/store.py` сейчас пустой SQLite-каркас: замени его адаптером PostgreSQL, не расширяй `SCHEMA`. Единственная новая зависимость шлюза для базы — закреплённая в `requirements.txt` версия `psycopg[binary]`. Используй транзакции и параметры запросов.

До применения миграции владелец стенда должен назвать проект Supabase и схему. Не выбирай проект по дате создания. Серверная строка подключения — `GATEWAY_DATABASE_URL`, имя схемы — `GATEWAY_DB_SCHEMA`. Разные стенды используют разные схемы; `public` допустима только по явному назначению для показа. Проверяй имя схемы перед использованием в SQL, требуй TLS, выставляй `search_path` соединения. Секреты не печатай и не отдавай браузеру. Если база недоступна, останови операции шлюза с данными с понятной ошибкой; молча возвращаться к SQLite нельзя. Для разработки и интеграционных тестов используй локальный PostgreSQL с той же миграцией. В Supabase пока ничего не применено: миграции сначала создаются и проверяются в репозитории, затем применяются только к указанной схеме.

Создай версионированные SQL-миграции и команду на чистом Python для их проверки и применения. На этом этапе нужны таблицы:

| Таблица | Поля |
|---|---|
| `services` | `id`, `clinic_id`, `code`, `title`, `kind`, `specialist?`, `room?`, `partner_only`, `step_aliases` (массив), `is_active` |
| `service_followups` | `clinic_id`, `finding_code`, `service_code`, `position`, `due_days?`, `due_note?`, `is_default` |
| `finding_texts` | `clinic_id`, `finding_code`, `seen`, `means`, `approved`, `approved_by?`, `approved_at?` |
| `slots` | `id`, `clinic_id`, `service_id` → `services`, `specialist`, `place`, `format`, `starts_at`, `price?`, `external_id?` |
| `appointments` | `id`, `episode_id`, `step_id`, `patient_ref`, `slot_id?` → `slots`, `clinic_id`, `starts_at`, `place?`, `format`, `status`, `booked_by`, `booked_by_id`, `referral_id?`, `external_id?`, `cancelled_at?` |
| `threads` | `id`, `kind` (`patient`/`staff`), `clinic_id`, `patient_ref?`, `episode_id?`, `subject?`, `request_kind?`, `status`, `opened_by_role`, `opened_by?`, `closed_at?`, `closed_by?` |
| `messages` | `id`, `thread_id` → `threads`, `sender_role`, `sender_id?`, `body`, `event_code?`, `intent?`, `episode_id?`, `step_id?`, `actions`/`payload` (jsonb), `channel`, `for_patient`, `needs_action`, `resolved_at?`, `resolved_by?`, уникальный `dedupe_key?`, `read_at?` |
| `outcome_submissions` | `event_id`, `episode_id`, `step_id`, `physician_id`, `confirmed_at`, хэш точного тела итога |

Добавь технические поля времени для экранов и сортировки. `episode_id`, `step_id`, `patient_ref`, `clinic_id` и идентификаторы сотрудников — текстовые ссылки на ядро без внешних ключей; связи внутри шлюза — с ключами. Ограничениями базы обеспечь: слот нельзя занять дважды, у шага одна действующая запись, одна пациентская лента на пациента, уникальный `dedupe_key`. Включи RLS на каждой таблице без политик для клиентских ролей; проверь права серверной роли на выбранную схему. Ни строка подключения, ни ключ сервера не попадают в браузер.

Каталог и тексты наполняй синтетикой через серверный seed из прототипа, повторное наполнение идемпотентно. `start.py` без `--keep` пересоздаёт SQLite ядра и меняет ID эпизодов: до наполнения очищай только рабочие таблицы шлюза этой схемы (`slots`, `appointments`, `threads`, `messages`, `outcome_submissions`; в следующих заданиях список расширится), каталоги сохраняй. При `--keep` ничего не очищай. `--smoke` использует отдельную схему, никогда схему показа. Если эти условия нельзя выполнить, останавливай запуск до очистки. Юнит-тесты базы работают с поддельным адаптером без сети, интеграционные — с отдельной тестовой схемой PostgreSQL.

## Общие правила задания

Они важнее удобства и действуют на всех трёх этапах.

- **Действия врача выполняет только врач.** `manual-plan`, `revise-plan` и `outcomes` шлюз вызывает только из сессии врача. Сессии пациента и сотрудника не могут запустить их ни напрямую, ни цепочкой вызовов.
- **Кто действует, берётся из сессии.** `actor` и `physician_id` — идентификатор человека сессии. `evidence` шлюз составляет сам: «Пациент выбрал время в личном кабинете», «Запись по звонку».
- **Проекция для пациента.** Пациент получает: текст заключения, подтверждённого врачом, объяснение простыми словами, шаги (идентификатор, описание, статус, цикл, время записи, срок). Не получает: журнал, оценку и название модели, внутренние причины, идентификаторы сотрудников. Шаг вида `manual_review` пациенту показывается как «Врач уточняет план». Встроенный `GET /v1/patient/{ref}` не используй: в нём нет идентификаторов шагов, без которых не записаться.
- **Чужое не видно.** Запрос пациента к чужому эпизоду отвечает 404.
- **Ручной разбор определяется по `status` эпизода**, а не по непустому `manual_reason`: после плана врача причина в сервисе остаётся.
- **Шаги идут по очереди.** Сервис разрешает `offer` только для первого незавершённого шага. Остальным шагам цикла кнопку записи не показывай, вместо неё — «После предыдущего шага». Любой клинический шаг, включая анализы, закрывается итогом врача; напрямую завершается только `care_coordination`.
- **Преобразование «ответ сервиса → данные для экрана»** живёт в шлюзе, в модуле `views.py`, и покрыто тестами. Форму данных держи близкой к той, которую ждут экраны прототипа (эпизод с шагами, журналом и причиной), чтобы разметку почти не трогать. Время шлюз отдаёт в ISO; «сегодня», «вчера», «6 дней назад» считает браузер.
- **Незнакомое значение не роняет экран.** Неизвестные статус, причина, источник решения показываются как есть и пишутся в лог шлюза.

## Каталог услуг стенда

В прототипе шаг — это ключ услуги (`SERVICES`, `SLOTS`, `NEXT`), по нему находятся название, специалист, кабинет и слоты. В сервисе пути у шага только `kind` и свободный текст `description`. Чтобы экраны не гадали, наполни `services` и `service_followups` синтетическими данными прототипа и отдавай каталог через шлюз:

- услуги: название (оно же `description` шага в сервисе пути), `kind`, специалист, место, где выполняется — у себя или у партнёра. В каталог входят все шаги из `rules.demo.json` и из наполнения стенда;
- что врач может назначить после приёма: код находки → список услуг со сроком в днях и отметкой «выбрано по умолчанию». Источник — `NEXT` из прототипа, с заменой рентгена на КТ;
- названия исследований: `study_type` и `anatomy` → «КТ органов грудной клетки», «МРТ коленного сустава», «Маммография».

Шаг, описания которого нет в каталоге, показывается своим описанием с общими слотами: врач может назначить и свободный текст. В `next_steps` и в шагах `revise-plan` шлюз ставит `owner: "coordinator"` и `continue_on: "confirmed_outcome"` — те же значения, что сервис ставит сам.

## Этап 1. Пациент и координатор

### Шлюз

Предлагаемые маршруты. Названия можно поправить, правила доступа — нет.

| Маршрут шлюза | Роль | Что делает в сервисе пути |
|---|---|---|
| `GET /api/patient/episodes` | пациент | `GET /v1/episodes` и `GET /v1/episodes/{id}`, отбор по `patient_ref` сессии, проекция для пациента |
| `GET /api/catalog` | все роли | ничего: каталог услуг стенда |
| `GET /api/slots?episode=&step=` | пациент, сотрудник | ничего: слоты пока демо (см. ниже) |
| `POST /api/patient/episodes/{id}/steps/{step}/book` | пациент | шаг `open`: `offer` с временем выбранного слота, затем `confirm`. Шаг `offered`: `confirm` с временем выбранного слота |
| `POST /api/patient/episodes/{id}/steps/{step}/confirm` | пациент | `confirm` для времени, которое предложила клиника |
| `POST /api/patient/episodes/{id}/steps/{step}/ask` | пациент | ничего: обращение координатору сохраняется в шлюзе |
| `GET /api/staff/episodes`, `GET /api/staff/episodes/{id}` | сотрудник, врач | эпизоды, очередь (`/v1/staff/queue`), имена пациентов |
| `POST /api/staff/episodes/{id}/steps/{step}/{offer\|confirm\|attend\|cancel\|refuse\|lost_contact}` | сотрудник | одноимённый переход |
| `POST /api/staff/episodes/{id}/steps/{step}/complete` | сотрудник | завершение шага `care_coordination` |
| `POST /api/staff/episodes/{id}/{stop\|close}` | сотрудник | одноимённый вызов |

**Имена пациентов** шлюз берёт из сервиса клиники: `GET /v1/patients` с токеном своей клиники, соответствие `patient_ref` → имя. Эпизод без `patient_ref` показывай как «Пациент не указан». Карта, анамнез и направления — в задании 06.

**Объяснение простыми словами.** В прототипе это тексты `seen` и `means`. В продукте храни их в `finding_texts` по `(clinic_id, finding_code)`. Перенеси формулировки для четырёх кодов стенда: `approved: true` — у трёх кодов с утверждённым правилом, `false` — у `DEMO_MG_DENSITY`. Шлюз показывает объяснение только после подтверждения врачом и только если текст утверждён. Иначе пациент видит: «Заключение готово. Врач объяснит результат на приёме». Генерировать объяснение на лету нельзя.

**Слоты.** У сервиса пути нет расписания: это зона МИС. Генерируй демо-слоты на ближайшие рабочие дни, записывай их в `slots` и отдавай из базы с `"demo": true`. При записи связывай шаг с `appointments`; учти отказ внешнего сервиса пути и повтор вызова. Не показывай один слот свободным двум пациентам. `external_id` оставляй пустым, пока нет МИС. Слоты только в своей клинике: партнёры появятся в 06 и 07.

**Обращения пациента** («Не сейчас», «Перезвоните мне», «Другое время» для подтверждённой записи) сохраняй как `messages` с `intent` в одной пациентской ленте `threads`; показывай неразрешённые сообщения координатору в очереди. Шаг в сервисе пути при этом не меняется. В задании 07 модуль связи использует эти же записи, повторный перенос не нужен.

**Смена времени.** Сервис принимает `appointment_at` в любом переходе, поэтому пациент, которому клиника предложила время, может выбрать другое: это `confirm` с временем нового слота. У подтверждённой записи сменить время нечем: остаются `cancel` и `refuse`, после них эпизод встаёт на паузу до решения врача. Не имитируй перенос цепочкой вызовов от чужого имени. У координатора есть «Отменить запись» с предупреждением, что обращение вернётся врачу. Предложение добавить в сервис переход для переноса подтверждённой записи запиши в отчёт отдельной строкой: решать автору сервиса.

### Экраны

Переведи на данные шлюза и убери соответствующие демо-данные и локальные изменения состояния:

- пациент: «Главная», «Мой план», «Записи»;
- сотрудник: «Обращения», карточка обращения, «Запись и сопровождение».

После действия экран перечитывает данные с сервера и перерисовывается. Счётчики в меню обновляются при переходе между экранами и раз в 15 секунд, чтобы запись пациента в одном окне была видна координатору в другом.

Подписи статусов возьми из прототипа (`P_STATUS`, `S_STATUS`) и дополни: `cancelled` — «Запись отменена», `lost_contact` — «Нет связи с пациентом», `closed` — «Закрыт». Причины ручного разбора и паузы переведи для сотрудника:

| `manual_reason` | Текст |
|---|---|
| `rule_not_approved` | Правило ещё не утверждено клиникой: нужен план врача |
| `unknown_finding_code` | Для этой находки в клинике нет правила |
| `no_approved_rule` | Правило для этой находки есть, но не для этого исследования |
| `unsupported_protocol` | Для такого исследования в клинике нет маршрутов |
| `missing_patient_ref` | В заключении не указан пациент |
| `report_revision` | Пришла новая версия заключения: сверьте с прежним обращением |
| `cancel`, `refuse`, `lost_contact` | Запись отменена / Пациент отказался от шага / Нет связи с пациентом: нужен новый план врача |

Источник решения (`decision_source`) и события журнала тоже переводятся в шлюзе: «Правило, версия demo-rules-1», «План врача», «Итог приёма: врач …», «Врач изменил план».

В карточке обращения блок «Заключение по исследованию» показывает текст заключения из `source_report`, кто и когда его подтвердил и источник черновика (`source_model`). Вместо «Что извлечено из текста» — поля самого заключения: исследование, область, протокол, код находки. Строка «Учтено из карты» до задания 06 скрыта. Строка «Если нет времени» показывает «Другой филиал или помощь координатора», как в прототипе.

## Этап 2. Врач

| Маршрут шлюза | Роль | Что делает в сервисе пути |
|---|---|---|
| `GET /api/doctor/visits` | врач | шаги в статусах `confirmed` и `attended` |
| `POST /api/doctor/episodes/{id}/manual-plan` | врач | `manual-plan` |
| `POST /api/doctor/episodes/{id}/revise-plan` | врач | `revise-plan` |
| `POST /api/doctor/episodes/{id}/steps/{step}/outcome` | врач | `attend`, если шаг ещё в `confirmed`, затем `outcomes` с `source: "staff_form"` |

**Итог визита идемпотентен, если повтор совпадает до байта.** Сервис сравнивает весь итог, включая `confirmed_at`. `event_id` создаётся в браузере при открытии формы (`crypto.randomUUID()`). При первом вызове шлюз сохраняет `confirmed_at` в `outcome_submissions` по `event_id`; при повторе берёт прежнее значение. Повтор с другим эпизодом, шагом, врачом или содержимым — 409; для сверки содержимого сохрани его хэш. Двойное нажатие и перезапуск шлюза не создают второй итог. В `next_steps` у каждого шага все пять ключей, `due_at` — время или `null`.

Экраны: «Приёмы», «Обращения» в роли врача, окна «Итог приёма» и «План врача». Варианты следующих шагов берутся из `service_followups` по коду находки; врач может добавить шаг свободным текстом.

Для эпизода с причиной `rule_not_approved` шлюз отдаёт шаги неутверждённого правила как вариант. Врач видит их в окне «План врача» отмеченными и подтверждает или меняет. Вариант становится планом только после решения врача. До этапа 3 шаги варианта шлюз берёт из `service_followups`, после — из `GET /v1/rules`.

Флажок «Выписать электронный рецепт» в окне итога до задания 07 создаёт рецепт в данных вкладки, как в прототипе. Подпиши его «демо».

## Этап 3. Правила и аналитика

### Сервис пути: два эндпоинта для чтения правил

Экрану «Маршруты и правила» нужны правила, а песочнице — ответ маршрутизатора без создания эпизода. Копировать логику `Ruleset.plan` в шлюз нельзя: она разойдётся с сервисом. Добавь в `medmarshrut_path_service/service.py` два маршрута для администратора, оба только читают:

- `GET /v1/rules` → `{"version", "supported_protocols": [...], "rules": [...]}` — то, что загружено из файла, включая неутверждённые правила.
- `POST /v1/rules/dry-run` с телом `{"study_type", "anatomy", "protocol_name", "finding_code"}` → `{"dry_run": true, "steps": [...], "manual_reason": null | "...", "rule_version"}`. Вызывает `Ruleset.plan` и ничего не записывает. Пациента в песочнице нет, поэтому служебный псевдоним обработчик подставляет сам и только здесь.

Тесты — в `test_service.py`, две строки — в README сервиса и в `docs/api-contracts.md`. Это правка чужого кода: минимальный дифф, отдельная строка в отчёте.

### Шлюз и экраны

| Маршрут шлюза | Роль | Что делает |
|---|---|---|
| `GET /api/staff/rules`, `POST /api/staff/rules/dry-run` | сотрудник, врач | новые эндпоинты сервиса пути |
| `GET /api/staff/metrics` | сотрудник | `/v1/staff/metrics` и воронка, посчитанная по эпизодам |

«Маршруты и правила»: список правил только для чтения с версией и пометкой «утверждено» или «черновик». Песочница вызывает `dry-run`: сотрудник выбирает исследование и находку из списков и видит шаги или причину ручного разбора. Подпись под списком: «Правила утверждает клиника. Они меняются в файле правил вместе с версией».

«Аналитика»: три показателя и воронка считаются по настоящим эпизодам стенда. Над блоком подпись: «Данные демо-стенда». Калькулятор эффекта остаётся, его поля — допущения пользователя, так и подпиши.

## Экраны, до которых очередь ещё не дошла

После этого задания часть экранов всё ещё живёт на данных вкладки. Чтобы продукт оставался цельным:

- **«Что на снимке» у пациента и врача, «Снимок и заключение»** (до задания 05). Показывают демо-исследования. Действия, которые в прототипе создавали или меняли эпизод, — подтверждение заключения врачом, загрузка снимка пациентом — отключи: кнопка неактивна, рядом подпись «Пока недоступно на стенде» (в коде — комментарий со ссылкой на задание 05). Ссылки из демо-исследований на эпизоды убери.
- **«Новое обращение»** (до задания 07). Анкета работает до экрана результата. Создание маршрута отключено, подпись: «Пока недоступно на стенде». Разбор по ключевым словам для этих экранов пока остаётся.
- **«Документы».** Заключения — из настоящих эпизодов пациента, рецепты — из данных вкладки.
- **«Сообщения», «Связь с врачами», «Связь с пациентами», «Аптека», «Аптека и заказы», «Партнёры»** — на данных вкладки. Ссылки на эпизоды перепривяжи к настоящим эпизодам стенда по `patient_ref`. Ссылку, которую привязать не удалось, убери вместе с кнопкой: битых переходов быть не должно.

## Что из прототипа в продукт не переносится

- **Разбор заключения по ключевым словам** (`analyze`, `detectModality`, `extractFacts`, регулярные выражения в правилах). В продукте маршрут строит только сервис пути по коду находки. С экранов маршрута эти функции уходят сейчас, с «Нового обращения» — в задании 07.
- **Выдуманные числа.** Воронка «Самостоятельные обращения» и показатели, которых нет в данных, убираются.
- **Переключатели без бэкенда** (настройки маршрутизации на экране правил, утверждение правила из интерфейса). Элемент управления, за которым ничего не стоит, не оставляй: подключи, убери или отложи до 07 с пометкой «демо».

## Тесты

- `views.py`: проекция пациента не содержит журнала, оценки и названия модели; шаг `manual_review` отдаётся без технического текста; эпизод со статусом `active` и непустым `manual_reason` не считается ручным разбором; незнакомые статус и причина не роняют преобразование.
- Доступ: пациент получает 404 на чужой эпизод; сотрудник и пациент получают 403 на действия врача; `actor` из тела запроса игнорируется.
- Запись пациента: для шага `open` в поддельный сервис уходят `offer` с временем слота и следом `confirm`; для шага `offered` — один `confirm` с новым временем.
- Итог приёма: для шага в `confirmed` уходит `attend`, затем `outcomes`; повтор с тем же `event_id` отправляет тот же `confirmed_at`.
- Сервис пути: тесты двух новых эндпоинтов.
- База шлюза: миграция в чистой тестовой схеме, изоляция схем, права серверной роли и RLS без клиентских политик, повторное наполнение каталога, занятость слота и идемпотентность `outcome_submissions` после перезапуска.
- `demo_stand/smoke.py`: проход через шлюз от имени своего пациента (сессия с его `patient_ref`): пациент записывается, сотрудник видит запись, врач вносит итог, у пациента появляется шаг второго цикла.
- `demo_stand/web_check.py`: экраны, переведённые на данные сервисов, убери из попиксельного сравнения с прототипом; проверку «открывается без ошибок в консоли» оставь для всех экранов. Сценарий из задания 03 замени сценарием на настоящих эпизодах.

## Готово, когда

- В трёх ролях экраны маршрута показывают эпизоды стенда: открытый шаг у «Демо-пациента», ручной разбор у Марии К., просроченный шаг у Олега Р., подтверждённую запись у Елены П., ожидание итога у Сергея Т.
- Сценарий в двух окнах: пациент записывается → у координатора меняется статус → врач вносит итог с двумя следующими шагами → у пациента появляется второй этап.
- Для Марии К. врач подтверждает вариант плана, обращение уходит из ручного разбора.
- Песочница правил отвечает так же, как сервис при настоящем заключении.
- На экранах, которые ещё не подключены, нет кнопок, которые ведут в никуда.
- Все наборы тестов зелёные, `python start.py --smoke` проходит.
