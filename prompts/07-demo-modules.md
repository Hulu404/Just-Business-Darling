# 07. Сервисы без бэкенда переезжают в шлюз

## Зачем

Из шести сервисов продукта три существуют только в интерфейсе: «Врач — клиника», «Клиника — пациент», маркетплейс с аптеками-партнёрами. К ним добавляется расписание, которое в настоящей клинике живёт в МИС. После заданий 04–06 эти разделы всё ещё хранят данные в памяти вкладки: врач в одном окне и пациент в другом друг друга не видят, обновление страницы стирает переписку и заказы.

В этом задании разделы переезжают в шлюз как отдельные модули с понятной границей. Кейс разрешает имитировать интеграции на демо; требование одно — имитация честно подписана и её легко заменить настоящим сервисом.

## Сначала прочитай

- `CLAUDE.md`, `docs/api-contracts.md` (события `outbox` сервиса пути), `docs/reports/04-path.md` … `06-clinic.md`.
- В `web/js`: экраны `messages`, `comms`, `requests`, `pharmacy`, `pharmacyAdmin`, `documents`, `intake`, `review`, `result`; справочники `TRIGGERS`, `PRODUCTS`, `PHARMACIES`; функции `notify`, `mkRequest`, `closeRequests`, `createPrescription`.
- В шлюзе: `services`, `service_followups`, `finding_texts`, `slots`, `appointments`, `threads`, `messages`, `outcome_submissions` из задания 04, `study_registry` из 05 и `referral_links` из 06.

## Что сделать

### Общее устройство

Папка `medmarshrut_gateway_service/modules/`: по файлу на модуль — `slots.py`, `messages.py`, `requests.py`, `pharmacy.py`. У каждого класс с методами и маршруты под `/api/`; все они используют адаптер PostgreSQL шлюза и **общие** таблицы там, где данные пересекаются. `messages.py` и `requests.py` работают с одной парой `threads`/`messages`; отдельные таблицы для обращений пациента и запросов врачу не создавай. `slots.py` использует `services`/`slots`/`appointments` из задания 04, не заводит второе расписание. Экраны и остальной шлюз обращаются к модулям только через методы классов: заменить интеграцию можно другой реализацией этих методов. Зафиксируй их интерфейсы в отчёте.

### Миграция и целевой состав 23 таблиц шлюза

В отдельной версионированной миграции добавь недостающие таблицы к схеме заданий 04–06. Все значения идентификаторов — `text`, а ссылки на `patient_ref`, эпизод, шаг, клинику и сотрудника — без внешних ключей до переезда ядра. Внутренние связи шлюза оформляй внешними ключами. RLS включён на каждой таблице без клиентских политик; из браузера доступа к Supabase нет.

| Таблица задания 07 | Поля |
|---|---|
| `notification_scenarios` | `(clinic_id, code)` — ключ; `title`, `timing`, `description`, `enabled` |
| `patient_settings` | `patient_ref` — ключ; `notify_app`, `notify_sms`, `notify_messenger`, `quiet_hours` |
| `pharmacies` | `id`, `name`, `address`, `distance?`, `clinic_id?`, `is_active` |
| `products` | `id`, `category`, `name`, `form`, `price`, `is_drug`, `requires_prescription`, `is_active` |
| `cart_items` | `(patient_ref, product_id)` — ключ; `product_id` → `products`, `quantity` |
| `prescriptions` | `id`, `number`, `clinic_id`, `patient_ref`, `episode_id`, `step_id`, `physician_id`, `physician_label`, `issued_at`, `valid_until`, `status` |
| `prescription_items` | `(prescription_id, position)` — ключ; `name`, `form`; с каталогом товаров не связаны |
| `rx_offers` | `(prescription_id, pharmacy_id)` — ключ; `availability`, `price` |
| `orders` | `id`, `number`, `type` (`otc`/`rx`), `patient_ref`, `pickup`, `pharmacy_id?`, `appointment_id?`, `prescription_id?`, `pickup_code?`, `delivery_fee`, `total`, `status`, `expires_at?` |
| `order_items` | `(order_id, product_id)` — ключ; `quantity`, `price` |
| `gateway_state` | `key`, `value` (jsonb); только явное демо-состояние, например сдвиг расчётного времени |

После миграции **21 рабочая таблица**: 8 из задания 04, по одной из 05 и 06, 11 здесь. Ещё две таблицы зарезервированы для необязательного задания 10: `ai_code_map` (`source_system`, `finding_class`, `finding_code`) и `ai_drafts` (`id`, `clinic_id`, уникальная пара `source_system`/`external_id`, `model`, `study_type`, `study_uid`, `anatomy`, `protocol_name`, `patient_ref?`, `finding_class`, `ai_conclusion`, `confidence?`, `payload_sha256`, `status`, `physician_id?`, `conclusion?`, `decided_at?`, `reject_reason?`). Создай их отдельной миграцией с ограничениями повторной доставки и решения врача, но **не** добавляй вход внешнего ИИ, экраны и изменение сервиса пути: это только задание 10. Итого 23 таблицы модулей шлюза. `gateway_state` не хранит секреты или персональные данные.

Ограничениями БД и серверной проверкой обеспечь одну действующую бронь на рецепт, отсутствие рецептурного товара в корзине и обычном заказе, выдачу «в день приёма» только при действующей записи. Каталоги аптек и товаров наполни только синтетикой. `rx_offers` — предложение аптеки для **конкретного рецепта**, не глобальная витрина наличия. Не создавай прежние `pharmacy_offers` и `rx_reservations`.

Каждый ответ модуля несёт `"demo": true`. В интерфейсе у заголовка таких разделов стоит метка «демо», на «Карте сервисов» — «демо-модуль шлюза». Справочники (товары, аптеки, имена врачей в слотах) возьми из прототипа и наполни ими таблицы шлюза серверным seed. JSON в `demo_stand/` допустим только как вход наполнения, не как источник данных работающего шлюза. Названия препаратов условные: «Препарат А» остаётся «Препаратом А».

### Расписание (`slots.py`)

Расширь `slots.py` из задания 04: слоты на ближайшие рабочие дни для своей клиники и для партнёров из `route-candidates`. Используй те же `slots` и `appointments`; слот занимается при записи и освобождается при отмене, дважды один слот не выдаётся. Слот у партнёра доступен, только если по шагу есть направление в статусе `accepted`: до этого — подсказка «Сначала партнёр должен принять направление». Это демо-зеркало МИС; внешний идентификатор пуст до настоящей интеграции.

### «Клиника — пациент» (`messages.py`)

- **События.** Модуль читает `GET /v1/staff/outbox` сервиса пути, помнит идентификатор последнего обработанного события и превращает новые события в сообщения пациенту. Чтение происходит при обращении к сообщениям и после каждого действия, которое шлюз выполнил в сервисе пути; фоновый поток не нужен. `patient_ref` события берётся из эпизода.

  | Событие сервиса пути | Сообщение пациенту | Выключается |
  |---|---|---|
  | `episode_created`, эпизод `active` | результат готов: ссылка на «Что на снимке» и предложение записи | сценарий `ready` |
  | `episode_created`, эпизод `manual_review` | заключение готово, план уточняет врач | сценарий `ready` |
  | `step_offered` | клиника предложила время: подтвердить или выбрать другое | нет, служебное |
  | `step_confirmed` | вы записаны: когда и куда | нет, служебное |
  | `plan_updated` после итога врача | план обновлён: новые шаги и рецепт | сценарий `after` |
  | `step_cancelled`, `step_refused`, `step_lost_contact` | пациенту ничего; задача координатору | — |

  В событии нет автора. Когда пациент записывается сам, сервис пути выдаёт `step_offered` и следом `step_confirmed`: сообщение «клиника предложила время» в этом случае не создавай. Шлюз знает, какие записи он сделал от имени пациента.
- **Кнопки в сообщении** ведут в настоящие действия из задания 04: «Выбрать время», «Подтвердить», «Перезвоните мне», «Не сейчас».
- **Напоминания по времени** — сценарии `remind4`, `call24`, `before`, `overdue` из `TRIGGERS`: запись не выбрана через 4 часа, пациент молчит сутки, визит завтра, шаг просрочен. Считаются при чтении по времени событий и по `due_at`. Для демонстрации добавь на экран координатора кнопку «Показать, что будет через сутки»: она сдвигает расчётное время модуля вперёд и подписана как демо-управление.
- **Переписка.** Пациент пишет координатору, координатор отвечает из карточки обращения и с экрана «Связь с пациентами». Используй уже сохранённые в задании 04 `threads`/`messages`; не копируй обращения. `kind=patient` — одна лента на пациента. «Не сейчас», «Перезвоните мне» и анкета — сообщения с `intent`, доступные в очереди координатора до `resolved_at`.
- **Экран координатора.** Таблица отправленного, показатели и шесть переключателей сценариев из `TRIGGERS`. Переключатель действительно выключает сценарий.
- **Каналы.** Настройки пациента сохраняются, но доставка только одна — в личный кабинет. SMS и мессенджеры не подключены: в колонке «Канал» так и написано. Правило прототипа остаётся правилом продукта: текст заключения в сообщения не попадает, в них только ссылка на раздел кабинета.

### «Врач — клиника» (`requests.py`)

- Запрос привязан к эпизоду, у него тема, переписка и статус. Это `threads.kind=staff` и сообщения той же таблицы `messages`, без отдельной таблицы запросов.
- Запрос врачу создаётся сам, когда эпизод попадает в ручной разбор или на паузу (действие `request_physician_plan` в очереди сервиса пути), и закрывается сам, когда врач утвердил или изменил план через шлюз. Для ручного разбора допускается только один открытый запрос на эпизод: закрепи это ограничением базы и проверь повторное чтение очереди.
- Врач создаёт запрос координаторам из окна итога приёма и с экрана «Связь с клиникой»; координатор отвечает и закрывает.
- Быстрые действия в запросе («Подтвердить маршрут», «Задать свой план», «Перейти к записи») вызывают настоящие действия из задания 04 и доступны только той роли, которой положено.

### Маркетплейс и аптеки (`pharmacy.py`)

- Каталог товаров без рецепта из `products`, корзина из `cart_items`, заказ `orders.type=otc` с позициями `order_items` и выбором места выдачи. «Заберу в день приёма» предлагается, только если у пациента есть подтверждённая запись в сервисе пути.
- Электронный рецепт создаёт врач в окне «Итог приёма». `prescriptions`/`prescription_items` хранят связь с эпизодом и шагом и дословные позиции врача, без автоматического сопоставления с `products`. Рецепт появляется у пациента в «Аптеке», в «Документах» и в сообщении «План обновлён».
- Бронь рецепта — `orders.type=rx` со ссылкой на `prescriptions`, предложением конкретной аптеки из `rx_offers`, кодом выдачи и отменой. Одна действующая бронь на рецепт; отдельной таблицы броней нет. Экран «Аптека и заказы» у сотрудника показывает оба типа заказа одним списком.
- Ограничения, которые нельзя ослабить: рецептурный препарат нельзя положить в корзину и заказать с доставкой, только бронь по рецепту; модуль не подсказывает дозировки и замены; предупреждения из прототипа (продавец — аптека-партнёр, инструкция и противопоказания, выдача по рецепту) остаются на своих местах.

### «Новое обращение» без снимка

Сценарии «Что-то беспокоит», «Есть анализ или выписка», «Не получается записаться» и «После приёма» в прототипе строили маршрут по ключевым словам. В продукте так нельзя: маршрут появляется только из подтверждённого врачом заключения. Анкета остаётся, а результат меняется: она уходит координатору как обращение в модуле «Клиника — пациент», пациент видит «Обращение передано координатору, ответим в рабочее время». Экран срочного обращения при отмеченном тревожном признаке сохрани как есть. Файл из анкеты не загружается: сохраняется только его имя, как в прототипе, и это подписано.

### Последние данные вкладки

После этого задания в браузере не остаётся стартовых демо-данных: `demo-data.js` содержит только справочники оформления (иконки, подписи). Кнопка «Сбросить демо» переименовывается в «Сбросить демо-модули» и вызывает `POST /api/demo/reset`: она очищает рабочие данные связи и аптеки **только текущей схемы** (`threads`, `messages`, `cart_items`, `prescriptions`, `prescription_items`, `rx_offers`, `orders`, `order_items`, `gateway_state`, `patient_settings`). `slots` и `appointments` оставь: их удаление осиротит подтверждённые шаги в сервисе пути. Каталоги (`services`, `service_followups`, `finding_texts`, `notification_scenarios`, `pharmacies`, `products`), мостики (`outcome_submissions`, `study_registry`, `referral_links`), данные сервисов и зарезервированные таблицы задания 10 тоже не трогай. Порядок удаления учитывает внешние ключи. В подсказке у кнопки объясни, что полный чистый стенд создаёт `python start.py` без `--keep`.

При чистом `start.py` очищай **все рабочие таблицы шлюза** до seed, включая три мостика: SQLite ядра пересоздаётся и ID эпизодов меняются. Каталоги оставляй, обновляй идемпотентно. При `--keep` очистки нет. Каждый стенд, `--smoke` и браузерная проверка используют отдельную, явно назначенную схему; перед сбросом проверяй схему, иначе останавливайся. Не допускай, чтобы два стенда с одинаковыми `demo-patient-1` одновременно пользовались одной схемой. Секреты подключения только у серверных процессов.

`demo_stand/seed.py` дополняется наполнением модулей. Модули — часть шлюза, поэтому наполняются через его маршруты от имени ролей, состояние эпизодов из задания 01 при этом не меняется:

- запрос врачу по обращению Марии К. создаётся сам: эпизод в ручном разборе;
- запрос координаторам от врача по обращению Олега Р.: «Просрочена контрольная КТ»;
- рецепт для Олега Р., привязанный к его завершённому первому шагу. Для этого у модуля аптеки есть маршрут наполнения; он принимает только токен `GATEWAY_SEED_TOKEN`, который `start.py` выдаёт шлюзу и скрипту наполнения;
- заказ без рецепта от имени Марии К. в статусе «Готов к выдаче».

## Тесты

- Сообщения: каждое событие `outbox` обрабатывается один раз; выключенный сценарий не создаёт сообщение; текст заключения не попадает ни в одно сообщение.
- Запросы: создаются при ручном разборе, закрываются после решения врача; быстрые действия недоступны чужой роли.
- Аптека: рецептурный препарат нельзя заказать как товар; бронь без рецепта не создаётся; пациент не видит чужие рецепты и заказы.
- Слоты: один слот нельзя занять дважды; слот партнёра недоступен без принятого направления.
- Сброс очищает только таблицы модулей.
- Миграции дают 23 таблицы в чистой тестовой схеме, повторное применение не теряет данные; схемы разработки и смоука изолированы, RLS не открывает чтение клиентским ролям. Чистый запуск удаляет старые ссылки на эпизоды, `--keep` сохраняет их; кнопка сброса сохраняет каталоги и мостики.
- `demo_stand/smoke.py`: после итога приёма с рецептом у пациента появляются сообщение, второй этап и рецепт; бронь в аптеке проходит; при записи пациента из кабинета сообщение «клиника предложила время» не создаётся.
- `demo_stand/web_check.py`: попиксельное сравнение с прототипом больше не выполняется ни для одного экрана — удали его; обход экранов и сценарии остаются.

## Готово, когда

- Главный сценарий идёт в двух окнах браузера без обновления вручную: пациент получает сообщение о результате → записывается → врач вносит итог и рецепт → пациент видит новый этап и бронирует препарат → координатор видит бронь.
- Обновление страницы ничего не стирает.
- В `web/js` нет стартовых данных пациентов, эпизодов, сообщений и заказов.
- У каждого демо-раздела видна метка «демо».
- Все наборы тестов зелёные, `python start.py --smoke` проходит.
